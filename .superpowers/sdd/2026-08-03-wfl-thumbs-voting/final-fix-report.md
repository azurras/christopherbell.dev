## Before-Edit Brief

- **Behavior:** Production candidate validation restores a current verified backup into one uniquely named disposable database, runs the candidate and V013 only against that clone, and drops only that clone. The old 8080 writer is stopped before the new release can begin live V013; a failure after the new-service start boundary leaves the website stopped/unready and reports a forward-only repair failure without restarting the prior binary. Both vote endpoint forms reject legacy `rating` and other unknown properties, including null-valued properties. Authenticated Favorites and Top Liked cards expose accessible UP/DOWN controls whose visible state changes only from the newest server-confirmed response, while anonymous Top Liked remains public and performs no detail fetch. Vote summaries wrap on narrow cards. Existing Java enrichment behavior remains unchanged while private helper names use vote terminology.
- **Invariants:** Candidate database names are generated internally and must match one strict bounded pattern; restore and cleanup receive structured native-process arguments, always map from `christopherbell.*`, and can never target `christopherbell`. Candidate cleanup runs on success and failure. No candidate process or database operation touches live data. No old-binary restart or current-junction rollback occurs after the live-migration boundary. Vote JSON accepts only the documented fields without weakening null, numeric, unknown-string, authentication, CSRF, or restaurant-not-found handling. Each restaurant owns an independent mutation generation; active-vote clicks remain idempotent; stale success/failure cannot replace newer confirmed state; failures restore controls and preserve confirmed state. Anonymous Top Liked renders summaries and links without vote controls or per-item detail reads. Large summaries wrap without horizontal overflow.
- **Boundary/API:** The operational boundaries are `Invoke-ProductionDeploy`, candidate database setup/cleanup helpers, and `Switch-ProductionRelease` in `Production.Deploy.psm1`. HTTP boundaries are `RestaurantVoteRequest` and `RestaurantVoteSetRequest` as deserialized by both controller routes. Browser boundaries are an injectable `wfl-list.js` initializer/controller, the existing `restaurant-vote-mutation.js` generation owner, the public top-liked/favorites list APIs, and the existing vote API. CSS remains scoped to WFL list/profile selectors. Java private enrichment helpers become `toVoteDetail`, `toVoteDetails`, and `applyVoteSummaries` (including the session equivalent) without changing public signatures.
- **Effects and failures:** Deployment effects are backup creation, namespace-mapped clone restore, candidate JVM startup/termination, exact clone deletion, Windows service stop/start, junction mutation, and HTTP verification. Backup archives and SHA sidecars are preserved; no automatic data restore is added. Candidate/setup/cleanup failures preserve causal exceptions and occur before any production stop. After the new-service start attempt, failures trigger only a bounded stop/unready postcondition and an actionable forward-only exception. Browser effects are list/freshness reads and authenticated vote/favorite writes; only response ownership mutates card state, and local errors do not replace the list. Refactors have no new effects.

## Deployment State-Machine Review

1. `Invoke-ProductionDeploy` resolves and builds the release without changing the live database or listener.
2. `Invoke-CandidateReleaseValidation` generates one name matching `^cbell_candidate_[0-9a-f]{12}_[0-9a-f]{24}$`, creates and dry-run-verifies a live backup, namespace-restores only `christopherbell.*` into that candidate name, and launches the port-8081 candidate with `SPRING_MONGODB_DATABASE` set to the clone. Therefore V013 can run only against the restored clone during candidate validation.
3. Candidate cleanup runs in `finally`. Both PowerShell and the fixed `mongosh` program revalidate the exact generated name; the value is supplied through an environment variable rather than interpolated into executable script. Candidate failure plus cleanup failure is preserved as an aggregate exception. The verified archive and sidecar are never deleted.
4. Only after candidate cleanup completes does `Switch-ProductionRelease` stop `ChristopherBellDev` and verify the production listener is gone. Junction changes occur with no old writer running. Failures before the new-start boundary may restore the compatible old junction because no new binary has been allowed to migrate live data.
5. The code marks the live-migration boundary immediately before the first new-service start attempt. From that point, all startup, migration, readiness, endpoint, and public-route failures enter the forward-only branch. That branch performs only the bounded website stop/postcondition; it does not point `current` back to the old release, call `Start-Service` for the old binary, or restore MongoDB.
6. A post-boundary failure reports either an actionable `InvalidOperationException` confirming stopped/unready state or an aggregate exception containing both the deployment cause and an inability to prove the stop postcondition. The operator guidance says to preserve the backup/evidence and repair or deploy forward, with production restore requiring separate explicit approval.
