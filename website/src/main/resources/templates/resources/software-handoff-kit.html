Software project handoff checklist

Use these six steps when an independent developer hands a small project to its next maintainer. Start with the project's agreed scope and adapt the records to the work actually delivered.

  1. Name the delivered version. List the repository, release archive, documentation, and other agreed assets separately. Record a release or revision for each one, so the recipient can identify the exact work being handed over.
  2. Name the receiving owners. Identify who will maintain each asset and who handles hosting, domain renewals, and billing. Keep unresolved responsibilities visible until the intended owners acknowledge them.
  3. Verify recipient access. Use the service's approved sharing process, then record what the recipient could actually open or do with their own access. A sent invitation or a link that works for the author is not evidence of completed access transfer.
  4. Record acceptance observations. Compare the agreed checks with actual results on the named environment and version. Label failed and untested checks explicitly, and record the receiving owner's response separately from the author's test results.
  5. Explain everyday operation and recovery. Point to the project's startup, maintenance, backup, and recovery instructions. Name the person responsible for each operation. Keep credentials in the established secure system, outside the handoff record.
  6. Assign the remaining work. Give each open item an owner, next action, and review date. Send the handoff with those items visible, then record questions or acknowledgment rather than treating silence as acceptance.

Fictional delivery record

This small example is fictional. It illustrates one inventory entry, not a customer result, testimonial, or the full kit's worked example.

Asset
A-01: Invoice Viewer release archive and README
Version
Release 1.2.0, matching the delivered source revision
Receiving owner
The client's designated application maintainer
Observed receipt
The maintainer opened the archive and README using their own access. The delivery thread records that observation.
Outstanding work
Still open: production deployment. The maintainer owns the next action: test the release in the agreed test environment, record the results, and review the deployment decision on the agreed review date.
Current status
Files received; production deployment and final acceptance remain open.

The record distinguishes receiving files from deploying or accepting them. Replace the example with your own project's actual links, version, observations, owner, and review date.

Try it on one deliverable

  1. Download the free inventory worksheet and open it in a text editor.
  2. Describe one deliverable, its version, and who will maintain it.
  3. Confirm the intended recipient can open the link, then record the evidence of receipt.

Keep passwords, tokens, and other credentials out of the worksheet. Use your established secure access-transfer process separately. Opening a link yourself does not verify the recipient's access.
